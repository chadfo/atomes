# CLAUDE.md — atomes.studio

Site vitrine de l'agence d'architecture Atomes studio (Simon Charles, architecte HMONP, Toulon / Hyères). Cinq pages : index, projets, a-propos, contact (message simple), devis (demande de devis). HTML statique + CSS + JS vanilla, sans build. Hébergé sur GitHub Pages, domaine atomes.studio. Lire README.md pour la structure, la charte et le contrat du formulaire.

## Règles
- Palette stricte : fond #171512, encre #ece7de, blanc #ffffff pour actif/hover, surfaces #1e1b17 (#221e19 au survol des projets), erreurs #d8896b. Pas d'autre couleur, pas d'arrondi, pas d'ombre.
- Typo : Archivo (titres, textes) + IBM Plex Mono (étiquettes en capitales, letter-spacing .12em). Google Fonts.
- Français, ton sobre. Ne pas réécrire les textes existants sans demande explicite.
- Responsive : nav hamburger < 640 px ; sections image/texte empilées < 980 px.
- Le formulaire de devis (devis.html, huit écrans, récapitulatif avant envoi) envoie vers la fonction `demande`, FormSubmit en secours. Garder le format de l'objet du mail `Nouveau projet — Type · Document · Commune (Nom)` ; pour un choix « Autre », la valeur devient `Autre : précision`. Chaque choix fermé (type, état du bien, documents, démarrage, source) a une option « Autre » avec un champ de précision, enregistré dans `projets.precisions`. Les règles de cohérence type → état du bien vivent dans `devis.js` (`BIENS_PAR_TYPE`, dupliqué dans la fonction `demande`) ; les cinq surfaces (`SURFACES`, toutes facultatives, avec définition derrière un bouton « ? ») sont listées dans `devis.js`, la fonction et `dossier.js` : modifier les trois ensemble, ainsi que les listes fermées (DOCS, CALENDRIERS, SOURCES). Pas de question sur le budget (choix de Simon).
- La page Contact (contact.html) sert aux prises de contact simples, distinctes des devis : question « Votre demande concerne-t-elle un devis ? » (oui → bouton vers devis.html), sinon coordonnées et message envoyés par FormSubmit à contact@atomes.studio, sans dossier. Objet `Nouveau message — Prénom Nom` (ou `— Société (Prénom Nom)`), à garder distinct de `Nouveau projet — …`. Menu : Accueil, Projets, À propos, Contact, Devis.
- Garder .nojekyll, robots.txt, sitemap.xml, favicon.png, l'image OG et les meta de chaque page.
- Le logo `<atom-logo>` (site/assets/js/atom-logo.js) est à conserver tel quel.

## Code
- Pas de style inline : tout dans `site/assets/css/site.css` (jetons `:root`, composants partagés, puis une partie par page). Utiliser les jetons (`var(--ink)`, `rgba(var(--ink-rgb),.55)`, `var(--pad-x)`…).
- Pas de `box-sizing:border-box` global (la mise en page d'origine n'en a pas) ; le poser explicitement là où il faut.
- Images : `site/images/<nom>.webp`, avec `alt` descriptif, `width`/`height` et `loading="lazy"` hors premier écran. Galerie d'un projet : `<template>` en fin de section dans projets.html.
- JS : un fichier par page (`projets.js`, `contact.js`, `devis.js`), chargé en `defer`, sans dépendance.
- `_archive/claude-design/` est la version d'origine (Claude Design) : référence uniquement, ne pas la modifier ni la publier.

## Démarrer
`npx serve site` puis ouvrir l'URL affichée. Rien à installer ni à compiler.

## Publication
Dépôt `chadfo/atomes`, branche `main` ; `site/` est déployé par `.github/workflows/pages.yml` (GitHub Actions) à chaque push. Commits en français ; ne pousser que sur demande de Simon.

## Espace client
- Backend : Supabase (Postgres + Auth par lien e-mail + Storage privé + Edge Functions `demande` pour le formulaire de devis et `espace` pour l'espace agence, les liens d'action reçus par e-mail, l'espace client et la réception des réponses des clients), Resend pour les e-mails (envoi depuis contact@atomes.studio ; réception sur le sous-domaine `r.atomes.studio`, webhook `email.received` vers `espace`, gardée le temps de la transition vers le moteur). Schéma et règles dans `supabase/migrations/`, fonctions dans `supabase/functions/`, guide dans SETUP-ESPACE-CLIENT.md. Chaque fonction reste un seul fichier (déployée par copier-coller dans l'éditeur Supabase) : petites fonctions utilitaires dupliquées, sans module partagé. Dupliqués entre `demande` et `espace`, à modifier ensemble : la timeline des e-mails (`timelineHtml`), le gabarit et la signature des e-mails.
- Identifiant de dossier : `AAMMJJHHMMSS` à l'heure de Paris, généré côté serveur (seconde suivante en cas de collision). Ne pas changer ce format.
- Fichiers : bucket privé `dossiers`, chemins `<id>/client/…` et `<id>/agence/…`. Jamais de bucket public, jamais la clé `service_role` ni aucun secret (`JETON_SECRET`, `RESEND_WEBHOOK_SECRET`…) dans `site/`.
- Front : `site/dossier/` + `assets/js/dossier.js` (espace client, consultation seule) et `site/admin/` + `assets/js/admin.js` (espace agence), supabase-js UMD depuis jsDelivr, version épinglée ; `site/action/` + `assets/js/action.js` (page ouverte par les liens des e-mails, sans supabase-js : `fetch` vers `espaceUrl`). Construire le DOM avec `textContent`, jamais `innerHTML` avec des données utilisateur. Mode démo : `?demo` (et `dossier/?demo=signature|paiement|production|validation|suivi|clos|retracte`, `action/?demo=signer|signer-pro|valider|renoncer`).
- Parcours v3 (14 octobre 2026, décisions de Simon, migration 0005) : tout par e-mail. Chaque e-mail au client montre la timeline du dossier ; son adresse de réponse est `MAIL_AGENCE` (contact@) depuis le moteur (avant : celle du dossier, `d<id>-<mac>@<REPONSES_DOMAINE>`, encore reçue par le webhook pendant la transition). Le client répond aux questions et demande une modification en répondant à l'e-mail : moteur de l'agence (voir plus bas) ou, pour les anciennes adresses, webhook Resend (signature Svix vérifiée) → table `messages` ; rattaché seul si l'expéditeur est l'e-mail du dossier (adresse simple, la même dans le champ `from` de Resend et dans l'en-tête From : `expediteurSur()`) et que Resend authentifie l'e-mail (DMARC « pass », ou DKIM « pass » = signature du domaine du From selon Resend ; jamais SPF seul ni un en-tête écrit par l'expéditeur : `authentifie()`), sinon « À vérifier » dans l'espace agence (rattacher ou supprimer) ; pièces jointes rangées dans `<id>/client/` (pas les images intégrées de la citation ni les petits logos) ; traitement reprenable (`messages.traite`, bail de 10 minutes : relivraison pendant le traitement = 503) ; limites par dossier et par 24 h ; texte reçu analysé en temps linéaire (pas d'expression régulière à retour arrière sur le contenu reçu). L'espace client est passif : timeline, documents, échanges et récapitulatif en lecture, aucune action (ni réponse, ni signature, ni paiement, ni validation, ni dépôt), sauf le lien légal « Renoncer au contrat ici » vers la page d'action. Signature du devis gérée par nous, sans Yousign : page d'action ouverte par un lien signé (`/action/#t=<jeton>`, HMAC avec `JETON_SECRET`, sans état ; modes signer, valider, renoncer), signature électronique simple sur l'empreinte et le montant affichés ; pour un particulier, case de démarrage anticipé obligatoire pour signer, jamais cochée d'avance. Jeton seulement dans le fragment : jamais dans un journal (`console.*`) ni dans une URL interrogée. Liens des e-mails toujours vers `SITE_URL` (l'origine de la requête ne sert qu'aux liens renvoyés à la page qui appelle). Le jeton de rétractation porte l'empreinte du contrat signé (`d`) : celui d'un contrat précédent est refusé. Paiement uniquement par virement, référence = numéro de dossier ; l'agence confirme avec « Virement reçu » (action `paye`). Plus de Stripe : ne pas le réintroduire (colonnes Stripe de 0004 laissées, inutilisées). Rétractation (particulier) : 14 jours après la signature, prolongés jusqu'au premier jour ouvrable ; enregistrée dans `projets.retracte_*`, l'étape ne change pas, plus aucun e-mail de mission ensuite. Confirmation du contrat et accusé de rétractation (obligations légales) : un e-mail non parti n'est jamais annoncé comme envoyé ; il est noté dans `projets.envois_echoues` et l'agence le renvoie (action `renvoyer`). Chaque action qui écrit au client renvoie `mail` (faux si l'e-mail n'est pas parti).
- Règles du parcours (modèle d'étapes de la migration 0004, inchangé) : 11 étapes dont 3 optionnelles (suivi administratif, masquées sans l'option) ; devis : un fichier par version (`devis-<id>-<AAMMJJHHMMSS>.pdf`), jamais écrasé, et un nouvel envoi remet à zéro signature, démarrage anticipé et rétractation (les anciens liens de signature ne valent plus) ; la timeline ne se modifie que par `projets.etape` (déclencheur `recalculer_etapes`). Le client n'écrit jamais directement en base ni dans Storage : sa demande passe par la fonction `demande`, ses e-mails par le moteur de l'agence, tout le reste par la fonction `espace` (Verify JWT désactivé, session, jeton ou signature Resend vérifiés dedans ; politique Storage « admin depose dans les dossiers »). Les listes d'étapes de la démo (dossier.js, admin.js, action.js) reprennent le modèle SQL : les tenir alignées. Avis clients en suspens (pas de fiche Google).
- Textes juridiques (case de démarrage anticipé, bouton « Signer et commander avec obligation de paiement », information et formulaire de rétractation, page « Renoncer au contrat ») : mot pour mot. Source : la fonction `espace` (e-mails, et page d'action qui les reçoit par `infos`) ; la démo de `action.js` en garde une copie, à tenir alignée. À faire valider par l'Ordre des architectes ; ne pas les reformuler sans demande de Simon.
- Le formulaire de devis garde FormSubmit en secours : ne pas retirer ce chemin.
- Moteur de l'agence (19 octobre 2026, voulu par Simon : le client écrit à contact@ ou simon@, pas à une adresse technique) : programme Python sur l'ordinateur de l'agence, dossier `atomes-moteur` à côté de ce dépôt (dépôt git local à part, jamais dans ce dépôt public ni dans `site/`). Module 1 « courrier » : lit contact@ et simon@ par IMAP (LWS, `mail.atomes.studio:993`, certificat vérifié avec la liste de Mozilla `certifi` et non le magasin de Windows, qui garde sur ce PC un « ISRG Root X2 » intermédiaire expiré ; lecture seule : EXAMINE et BODY.PEEK, rien n'est marqué lu), toutes les 5 minutes (tâche planifiée Windows) ; e-mail rangé dans le dossier du numéro de l'objet, sinon dans le dernier dossier de l'expéditeur ; inconnu sans numéro : ignoré ; vérifié si l'expéditeur est l'e-mail du dossier et que sa signature DKIM, contrôlée par le moteur (dkimpy), est alignée sur son domaine, sinon « À vérifier ». Il écrit avec une clé secrète Supabase (`sb_secret_…`, Gestionnaire d'identification de Windows) : `messages` (`resend_id = imap:<Message-ID>`, anti-doublon entre les deux boîtes ; `auth.controle = 'moteur'`), pièces dans `<id>/client/`, réponses aux questions, demandes de modification ; aucun e-mail envoyé. « Rattacher » un message du moteur (fonction `espace`) le marque `verifie = true, traite = false` : le moteur le traite au passage suivant depuis sa copie locale ; l'espace agence affiche « En attente du moteur ». Les règles de texte et de pièces jointes du moteur sont un portage de celles de `espace` (tests de parité contre le TypeScript dans le moteur) : modifier les deux ensemble. Suite prévue du moteur : plans de situation et de masse, ArchiCAD 27.
